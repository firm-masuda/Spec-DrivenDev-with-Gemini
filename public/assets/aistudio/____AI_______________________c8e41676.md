### 工程 01: 要求定義（Business Requirements Definition）

* **使用ツール:** Google AI Studio (Playground)
* **到達目標:** クライアントの要望から、ゲームのコア体験（In-Scope）と初期リリースでは作らない要素（Out-of-Scope）を明確に分離する。

#### 実践ステップ
1. Google AI Studio を開き、`Temperature: 0.2` に設定する。
2. 以下のプロンプトを入力して実行する。

```markdown
# 役割
あなたはゲーム開発およびソフトウェア設計に精通したシニアITアーキテクトです。

# 目的
以下のクライアントヒアリングメモから本質的な要求を抽出し、
「業務要求仕様書（docs/01_business_requirements.md）」をMarkdown形式で作成してください。

# 出力構成
1. プロジェクト背景と目的
2. コアゲーム体験とユーザーストーリー（As-Is / To-Be）
3. 成功基準（定量的目標：フレームレートの安定性、テスト自動化率など）
4. スコープ定義
   - 対象スコープ（In-Scope：基本ゲームループ、スコア計算、残機管理、ハイスコア保存）
   - 対象外スコープ（Out-of-Scope：オンラインランキング通信、BGM/効果音再生、複雑なパーティクル演出、マルチボールアイテムなど初期版で除外するもの）

# クライアントヒアリングメモ
社内イベントやプログラミング学習の題材として、Pythonで動くGUIの『ブロック崩しゲーム』を作りたい。
パドルを左右キーで操作してボールを跳ね返し、上部に並んだ複数段のブロックをすべて壊したらステージクリア、ボールを画面下に3回落としたらゲームオーバーにしたい。上段のブロックほど壊したときのスコアを高くし、ハイスコアをローカルファイル（JSON）に保存・表示できるようにしてほしい。
Ubuntu環境で標準ライブラリの `tkinter` を使ってPython 3.13で作りたい。また、GUI画面を開かなくてもゲームの計算ロジックや当たり判定を `pytest` で高速にテストできる構造にしてほしい。
```

3. 生成されたテキストを手元に控え、次工程の入力とする。

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **ゲームのスコープクリープ防止:** ゲーム開発は「アイテムを出したい」「音をつけたい」「ステージエディタを作りたい」と要求が無限に膨らみやすい領域です。工程01で「まずは純粋なブロック崩しのコア体験とテスト容易性に集中する」とOut-of-Scopeを定義することがプロジェクト完遂の鍵になります。
> * **低Temperatureの理由:** アイデア出しではなく論理的な構造化を求めるため、`0.2` 前後に抑えてハルシネーションと冗長な表現を抑制します。

### 工程 02: 要件定義（System Requirements Definition）

* **使用ツール:** Google AI Studio (Playground)
* **到達目標:** 曖昧な「ブロック崩し」を、座標系・速度ベクトル・当たり判定・状態遷移・非機能要件（60FPS = 1フレーム16.6ms以内）として数値定義する。

#### 実践ステップ
1. 工程01のチャットを継続し、以下のプロンプトを実行する。

```markdown
# 目的
確定した業務要求に基づき、エンジニアが実装・自動テスト可能な
「システム要件定義書（docs/02_requirements.md）」を作成してください。

# 出力構成
## 1. 画面・座標系およびエンティティ仕様
- キャンバスサイズ（例: 幅800px × 高さ600px）
- パドル（サイズ、初期位置、移動速度、画面端の移動制限）
- ボール（半径、初期位置、速度ベクトル `(vx, vy)`、反射ルール）
- ブロック配置（行数・列数、色、段ごとのスコア配点：例 1段目100点、2段目50点…）
## 2. ゲーム状態遷移ルール（State Machine）
- 状態一覧：`READY`（開始待機）、`PLAYING`（プレイ中）、`PAUSED`（一時停止）、`GAMEOVER`（残機0）、`VICTORY`（全ブロック破壊）
- 各状態間の遷移トリガー（スペースキー押下、Pキー押下、残機喪失、残ブロック0）
## 3. 非機能要件（測定可能な数値基準）
- 性能要件：60FPSの維持（1フレームあたりの物理更新処理 `tick()` が `2.0ms` 以内に完了すること）
- テスト容易性（Testability）：GUI描画（`tkinter`）に一切依存せず、純粋なPythonクラスのみで1フレームごとのゲーム進行と当たり判定をヘッドレス検証できること
- データ永続化：ハイスコア保存JSONファイルが破損していた場合でもクラッシュせず初期値（0点）で復旧すること
- 技術スタック制約：Ubuntu Linux, Python 3.13, 標準ライブラリ `tkinter`, `dataclasses`, `json`
```

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **ヘッドレステスト要件の明文化:** GUIアプリ開発で最大の落とし穴は、`tkinter.Canvas` の中に直接当たり判定やスコア計算を書いてしまい、画面を立ち上げないとテストできなくなることです。非機能要件で「ロジックの完全分離」と「1フレーム計算2.0ms以内」を定義しておくことで、後の自動テストループ（Self-Healing）が機能します。

### 工程 03: 基本設計 / 外部設計（Architectural & Basic Design）

* **使用ツール:** Google AI Studio × Antigravity Desktop
* **到達目標:** ロジック層（Model/Engine）と描画層（View/GUI）を完全分離するアーキテクチャを設計し、状態遷移図とクラス図を視覚レビューする。

#### 実践ステップ
1. **AI Studio** で以下のプロンプトを実行する。

```markdown
# 目的
`docs/02_requirements.md` を満たすための「基本設計書（docs/03_architecture.md）」を作成してください。

# 出力構成
## 1. アーキテクチャ設計（Model-View-Controller 分離パターン）
- **Model / Engine層（GUI非依存）**: 座標計算、衝突判定（AABB/円と矩形）、状態遷移、スコア計算を担う純粋Pythonモジュール
- **Storage層**: ハイスコアJSONの読み書きと破損時フォールバックを担うモジュール
- **View / Controller層（`tkinter` 依存）**: キャンバス描画、キー入力バインド、タイマーループ（`after` メソッド）のみを担う薄いラッパー
## 2. クラス図（Mermaid classDiagram）
- `Ball`, `Paddle`, `Brick`, `GameStatus`, `GameEngine`, `ScoreRepository`, `BreakoutApp(GUI)` の関係と主要メソッド
## 3. ゲーム状態遷移図（Mermaid stateDiagram-v2）
- `READY` / `PLAYING` / `PAUSED` / `GAMEOVER` / `VICTORY` の遷移図
## 4. 衝突判定（Collision Detection）アルゴリズム仕様
- 壁との反射、パドルとの反射（当たった位置による角度変化または単純反転）、ブロックとの衝突時の速度反転ルール
```

2. **Antigravity Desktop** を起動し、生成された `03_architecture.md` を読み込ませる。
3. Desktopのプレビュー画面で **Mermaidのクラス図と状態遷移図** をレンダリングし、以下を目視検証する：
   * `GameEngine` クラスが `tkinter` に一切依存していないか（依存矢印が向いていないか）。
   * `PAUSED` から `PLAYING` への復帰など、状態遷移に袋小路がないか。

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **依存関係の視覚チェック:** テキストのコードブロックだけでは、クラス間の不正な依存や状態遷移の抜け漏れに気づきにくいためです。Desktopのビジュアルレンダリング機能で図として俯瞰することで、実装前に設計バグを潰せます。

### 工程 04: 環境構築・品質ガードレール整備（Environment Setup）

* **使用ツール:** Antigravity IDE（内蔵ターミナル / Ubuntu Bash）
* **到達目標:** Ubuntuパッケージ（`python3-tk`）、`uv` 仮想環境、`Makefile`、不正コミット遮断フック（`pre-commit`）を構築する。

#### 実践ステップ
1. Ubuntu端末で以下のコマンドを実行し、`tkinter` ランタイムの確認とプロジェクト初期化を行う。

```bash
# 1. Ubuntu標準の tkinter パッケージ確認・導入（必要な場合）
sudo apt-get update && sudo apt-get install -y python3-tk

# 2. ワークスペース作成とGit初期化
mkdir -p ~/workspace/breakout && cd ~/workspace/breakout
git init -b main
mkdir -p docs src/breakout tests/unit tests/integration tests/load scripts .githooks

# 3. uv による Python 3.13 プロジェクト初期化と開発ツール導入
uv init --no-workspace --name breakout
uv add --dev pytest pytest-cov ruff

# 4. パッケージ初期化ファイル作成
touch src/breakout/__init__.py tests/__init__.py
```

2. 工程01〜03で作成した3つのMarkdownファイルを `docs/` 配下に保存する。
   * `docs/01_business_requirements.md`
   * `docs/02_requirements.md`
   * `docs/03_architecture.md`

3. プロジェクトルートに `Makefile` を作成する。

```bash
cat << 'EOF' > Makefile
SHELL := /bin/bash
.SHELLFLAGS := -eu -o pipefail -c
.DEFAULT_GOAL := help

UV_RUN := uv run
PYTHONPATH := PYTHONPATH=src
SRC_DIR := src
TESTS_DIR := tests
DOCS_DIR := docs

.PHONY: help setup run format lint test test-unit test-int verify commit rollback

help: ## コマンド一覧を表示
	@grep -E '^[a-zA-Z_-]+:.*?## .*$$' $(MAKEFILE_LIST) | awk 'BEGIN {FS = ":.*?## "}; {printf "  \033[36m%-15s\033[0m %s\n", $$1, $$2}'

setup: ## 環境同期とGitフックの有効化
	uv sync --all-extras
	git config core.hooksPath .githooks
	@echo "==> [OK] Environment and Git hooks configured."

run: ## ブロック崩しGUIアプリの起動
	$(PYTHONPATH) $(UV_RUN) python -m breakout.main

format: ## Ruffによるコードフォーマット
	$(UV_RUN) ruff format $(SRC_DIR) $(TESTS_DIR)

lint: ## Ruffによる静的解析
	$(UV_RUN) ruff check $(SRC_DIR) $(TESTS_DIR)

test-unit: ## 単体テストの実行（ヘッドレス高速実行）
	$(PYTHONPATH) $(UV_RUN) pytest $(TESTS_DIR)/unit -v

test-int: ## 結合テストの実行
	$(PYTHONPATH) $(UV_RUN) pytest $(TESTS_DIR)/integration -v

test: ## 全テスト（単体＋結合）およびカバレッジ計測
	$(PYTHONPATH) $(UV_RUN) pytest $(TESTS_DIR)/unit $(TESTS_DIR)/integration -v --cov=$(SRC_DIR) --cov-report=term-missing

verify: format lint test ## フォーマット・リント・全テストの一括検証
	@echo "==> [SUCCESS] All quality gates passed."

commit: ## 検証通過を条件とした安全なGitコミット (例: make commit m="feat: ...")
	@if [ -z "$(m)" ]; then echo "[ERROR] Usage: make commit m=\"feat(scope): message\""; exit 1; fi
	@$(MAKE) verify
	git add $(SRC_DIR) $(TESTS_DIR) $(DOCS_DIR) Makefile pyproject.toml .githooks
	git commit -m "$(m)"

rollback: ## 直前のクリーンコミットへ作業ツリーを完全復元
	git restore .
	git clean -fd
	@echo "==> [ROLLED BACK] Working tree is now clean at HEAD."
EOF
```

4. Gitフック（`pre-commit` および `commit-msg`）を設定し、ベースラインコミットを作成する。

```bash
# pre-commit: make verify の強制
cat << 'EOF' > .githooks/pre-commit
#!/usr/bin/env bash
set -euo pipefail
echo "==> [Git Hook] Running pre-commit verification (make verify)..."
make verify
EOF

# commit-msg: Conventional Commits 形式の強制
cat << 'EOF' > .githooks/commit-msg
#!/usr/bin/env bash
set -euo pipefail
commit_regex='^(feat|fix|docs|style|refactor|test|chore)(\([a-z0-9_-]+\))?: .+$'
if ! grep -qE "$commit_regex" "$1"; then
    echo "[ERROR] Invalid commit message format!"
    echo "Must follow Conventional Commits: <type>(<scope>): <subject>"
    echo "Example: feat(engine): implement ball collision logic"
    exit 1
fi
EOF

chmod +x .githooks/pre-commit .githooks/commit-msg
make setup

# 初期疎通テストを配置してベースラインコミット
cat << 'EOF' > tests/unit/test_sanity.py
def test_sanity() -> None:
    assert True
EOF

make commit m="chore(init): initialize breakout project and quality guardrails"
```

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **AIエージェントを統制する物理的ガードレール:** プロンプトで「リントを通して」「コミット規約を守って」と指示するだけでは、AIはしばしば規約を破ります。Gitフック（`pre-commit` / `commit-msg`）をOSレベルで仕込むことで、**テストが1つでも落ちているコードや規約違反のコミットメッセージを物理的に拒絶**する環境が整います。

3. 生成された計画書を確認し、コミットする。
   ```bash

   ```

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **GUI実装を最後（Phase 4）に回す理由:** 最初からGUI（`tkinter`）と一緒に作らせると、描画コードと物理演算が混ざり合い、バグの温床になります。Phase 1〜3で「画面なしでも完全に動くブロック崩しエンジン」を完成・テストし、最後のPhase 4でただそれを画面に描画するだけにするのが鉄則です。

### 工程 06: 実装 ＆ 単体テスト（Implementation & Self-Healing Loop）

* **使用ツール:** Antigravity IDE × Antigravity Desktop
* **到達目標:** Phase 1〜Phase 4 を1つずつ順番に実行し、内蔵ターミナルでの自動テストと自己修復（Self-Healing）を経てコミットを積み上げる。

#### 実践ステップ
1. **Antigravity IDE** で以下のプロンプトを実行し、Phase 1 を実装する（Phase 2〜4 も同様に1つずつ実行する）。

```markdown
# 目的
`docs/04_implementation_plan.md` の **「Phase 1: エンティティとデータモデル定義」** を実行してください。

# 実行ルール（自律ループ要件）
1. 対象ファイル（`src/breakout/models.py`）と対応する単体テスト（`tests/unit/test_models.py`）のみを作成・編集してください。先のPhaseのコードは書かないでください。
2. パドルの画面端移動制限（左端0未満・右端画面幅超えの防止）や矩形同士の重なり判定（AABB）の境界値テストを必ず含めてください。
3. 実装後、内蔵ターミナルで `make verify` を実行してください。
4. リントエラーやテスト失敗が発生した場合は、スタックトレースを解析して自律的にコードを修正し、**`make verify` が Exit Code 0 でパスするまで修正ループを継続**してください。
5. パスしたら `docs/04_implementation_plan.md` の Phase 1 チェックボックスを `[x]` に更新し、ターミナルで以下を実行してコミットしてください：
   `make commit m="feat(models): implement Phase 1 game entities and boundary unit tests"`
```

2. 同様に Phase 2（`engine.py`）、Phase 3（`storage.py`）、Phase 4（`gui.py` / `main.py`）を順番に実行・コミットさせる。
3. Phase 4 完了後、**Antigravity Desktop**（または端末から `make run`）でGUIウィンドウを立ち上げ、実際にパドル操作とボール反射が滑らかに動くか視覚的に確認する。

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **境界値バグの早期撲滅:** ブロック崩しで最も多いバグは「パドルが画面外に突き抜ける」「ボールが壁にめり込んで振動する」といった座標境界のバグです。Phase 1〜2の単体テストで座標の境界値を徹底的にアサートさせることで、GUIを立ち上げたときには既に物理演算が完璧な状態になります。

### 特別演習 (EX): 仕様変更の差分適用 ＆ 破綻からのロールバック

実務で必ず発生する「途中の仕様変更（追加ギミック要望）」と「実装失敗時の復旧」を体験する必須演習です。

#### 判断基準：仕様変更時にAI Studioへ戻るべきか？
* **小〜中規模（IDE内で完結）:** 今回の「ハードブロック追加」や「スコア計算式の変更」など、既存アーキテクチャの枠内で収まる変更は Antigravity IDE 内で設計書と実装計画を差分更新する方が圧倒的に高速です。
* **大規模（AI Studioへ戻る）:** 「シングルプレイからWebSocket通信によるオンライン対戦ゲームへ刷新する」といった根底のアーキテクチャ変更時のみ、AI Studio に戻ってゼロベースで基本設計をやり直します。

#### EX-1: 意図的な実装破綻とロールバック（Post-mortem 演習）
1. 手動またはプロンプトで `src/breakout/engine.py` の反射計算の符号を逆にするなどしてテストが落ちる状態を作り、以下のロールバック・診断プロンプトを実行する。

```markdown
# 目的
現在発生しているテスト失敗・不整合を解消するため、直前の安定コミットへロールバックし、原因を事後診断（Post-mortem）してください。

# 実行手順
1. 現在の `git diff` と `make test` のエラー出力を確認・記憶してください。
2. 内蔵ターミナルで `make rollback` を実行し、`git status` が clean であることを確認してください。
3. チャット上に以下の診断レポートを出力してください：
   - **根本原因 (Root Cause)**: どの計算式の変更によってどのテストが破壊されたか
   - **次回試行時の必須制約 (Actionable Rules)**: 再発を防ぐための具体的な実装ルール
```

#### EX-2: 仕様変更の安全な差分計画・実装（Regression 防止演習）
1. クライアントから「耐久力2の硬いブロック（シルバーブロック）を追加したい」という仕様変更が来た想定で、以下のプロンプトを投入する。

```markdown
# 目的
以下の仕様変更について影響範囲を解析し、既存テストを壊さない差分実装計画を `docs/04_implementation_plan.md` に追加してください。

# 追加仕様
「最上段（1段目）のブロックを『ハードブロック（耐久力 `hit_points = 2`）』とする。ボールが1回当たると耐久力が `1` に減り（破壊されずボールは反射）、2回当たると破壊されてスコア（200点）が加算される。2段目以降は従来通り耐久力 `1` とする。」

# 実行手順
1. 影響を受けるモデル（`Brick`）・エンジン（`GameEngine`）・GUI描画（色変化など）・既存テストを特定し、チャットに報告してください。
2. `docs/02_requirements.md` に仕様を追記してください。
3. `docs/04_implementation_plan.md` の末尾に完了済みタスクを残したまま **「Phase 5: ハードブロック（複数耐久力）仕様の追加」** を追加してください。
4. 続けて Phase 5 の実装と単体テスト追加を行い、既存のテストを含め `make verify` が全件パスすることを確認した上で、`make commit m="feat(engine): add multi-hit durability for top-row bricks"` を実行してください。
```

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **泥沼化の防止と下位互換性の維持:** AIがバグ修正に失敗して当て推量のパッチを重ね始めるとコード全体が崩壊します。「おかしくなったら即 `make rollback` でクリーンに戻す」習慣と、既存テストを壊さないようデフォルト引数（`hit_points: int = 1`）等で下位互換性を保つ改修パターンを習得します。

### 工程 07: 結合テスト（Integration Testing）

* **使用ツール:** Antigravity IDE
* **到達目標:** ゲーム開始からブロック全破壊（クリア）、ゲームオーバー、およびハイスコアのJSONファイル保存・再読込までを一気通貫で結合検証する。

#### 実践ステップ
1. Antigravity IDE に以下のプロンプトを投入する。

```markdown
# 目的
基本設計書（`docs/03_architecture.md`）に基づき、`GameEngine` と `ScoreRepository` を結合した通しシナリオテストを `tests/integration/test_game_lifecycle.py` に作成してください。

# 検証シナリオ要件
1. **ゲームクリア＆ハイスコア更新シナリオ**:
   - 一時ディレクトリ（`tmp_path` フィクスチャ）のJSONファイルを使用する。
   - ゲームを開始（`PLAYING`）し、残りのブロックをすべて破壊する状態まで `tick()` を進め、状態が `VICTORY` に遷移すること、および獲得スコアがJSONファイルにハイスコアとして正しく永続化されていることを検証する。
2. **ゲームオーバー＆ハイスコア維持シナリオ**:
   - 既存のハイスコア（例: 1000点）が保存されている状態で新規ゲームを開始し、スコア0点のままボールを3回落として `GAMEOVER` に遷移させる。JSONファイルのハイスコアが0点で上書きされず、1000点のまま維持されていることを検証する。
3. 実装後、`make verify` を実行し、全テストパス後に `make commit m="test(integration): add full game lifecycle and high-score persistence tests"` でコミットしてください。
```

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **エンジンとストレージの連携検証:** 「ゲームには勝ったがハイスコアがファイルに書き込まれていなかった」「低いスコアを出したときに過去のハイスコアを上書きして消してしまった」といったモジュール間連携のバグを結合テストで確実に仕留めます。

### 工程 08: システムテスト / 総合テスト（System & Non-Functional Testing）

* **使用ツール:** Antigravity IDE × Antigravity Desktop
* **到達目標:** 要件定義書で定めた非機能要件（1フレーム処理2.0ms以内＝60FPS余裕達成、破損JSONファイルからのクラッシュ回避）を実測検証する。

#### 実践ステップ
1. Antigravity IDE に以下のプロンプトを投入し、非機能・性能検証テストを実行する。

```markdown
# 目的
`docs/02_requirements.md` の非機能要件（性能・耐障害性）を検証するシステムテストを `tests/load/test_non_functional.py` に作成・実行してください。

# 検証内容
1. **フレームレート性能要件検証（60FPS保証）**:
   - ゲーム開始状態で `engine.tick()` を連続 `10,000フレーム`（約166秒相当のゲーム進行）実行し、1フレームあたりの平均処理時間および99パーセンタイル処理時間が `2.0ms` 以内であることを計測・アサートする。
2. **破損データ耐障害性検証（Resilience）**:
   - ハイスコアJSONファイルに不正なバイナリや壊れたJSON文字列（`"{broken_json"`）を書き込んだ状態で起動・読込を行い、例外でクラッシュせず初期値 `0` にフォールバックして正常にゲームが開始できることを検証する。
3. 内蔵ターミナルで `PYTHONPATH=src uv run pytest tests/load -v -s` を実行し、実測された1フレーム処理時間をチャットに報告してください。
```

2. テストパスを確認し、コミットする。
   ```bash
   make commit m="test(system): add 10k-frame performance benchmark and corrupted file resilience tests"
   ```

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **長時間プレイ時の速度低下検出:** オブジェクト管理にバグ（破壊済みブロックがメモリから消えず毎フレーム判定が増え続ける等）があると、プレイ開始数分後にFPSが急落します。10,000フレームの連続負荷試験をヘッドレスで回すことで、約1秒で長時間稼働時の性能劣化を証明できます。

### 工程 10: システム移行・実運用開始（Migration & Cutover）

* **使用ツール:** Antigravity IDE（内蔵ターミナル）
* **到達目標:** 旧イベント時のスコア記録（CSV形式）から新システムのハイスコアJSONへデータを引き継ぐ移行スクリプトを作成・リハーサルし、リリースタグ（`v1.0.0`）を打つ。

#### 実践ステップ
1. Antigravity IDE に以下のプロンプトを投入し、過去スコアの移行スクリプトを作成・検証する。

```markdown
# 目的
過去のイベントで記録されたスコア一覧（CSV形式：`player_name,score,recorded_at`）から最高得点を抽出し、本アプリのハイスコアJSONファイルへ安全に移行するスクリプト `scripts/migrate_scores.py` とその単体テストを作成してください。

# 要件
1. CSV内の最大スコアを抽出し、現在のハイスコアJSONの値より高い場合のみ更新すること。
2. 不正な行（数値変換エラーや負のスコア）が含まれる場合はエラー報告して中断すること。
3. ファイルを実際には書き換えず検証結果のみを表示する `--dry-run` オプションを実装すること。
4. テストを作成して `make verify` をパスさせ、ターミナルで `--dry-run` の実行リハーサルを行ってください。
```

2. 全検証通過後、最終コミットとリリースタグ（`v1.0.0`）を作成する。

```bash
make commit m="feat(migration): add legacy CSV score migration script with dry-run support"
git tag -a v1.0.0 -m "Release v1.0.0: Breakout GUI application production release"
git log --oneline --decorate -n 10
```

> 💡 **なぜこの手順が必要か（設計意図メモ）**
> * **リリースエンジニアリングの完結:** コードを書いて終わりではなく、旧資産からのデータ引き継ぎ（`--dry-run` リハーサル付き）とセマンティックバージョニング（`v1.0.0` タグ）までを一連のパイプラインとして締めくくります。
